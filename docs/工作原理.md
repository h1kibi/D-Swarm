# Project D-Swarm · 工作原理 (How it works)

D-Swarm 让一群异构的编码 Agent（Claude Code / Codex / cursor-agent）扑同一道题，在一张**共享黑板**上协作：谁发现的事实大家都能用，谁走过的死路大家都不再试，而 flag 只有**逐字出现在真实执行输出里**才被接受。核心不是「换个更强的脑子」，而是 **异构 + 共享证据 + 溯源闸门**。

而 worker 是怎么把数据交到平台、又怎么看到队友进展的？**全靠每个 worker 内置的 `dswarm-blackboard` skill**——这是 worker 与黑板之间唯一的数据通道。

---

## 一张图看懂：SharedGraph × ReasonScheduler 循环

一次 run 只有一条正式执行路径：准备运行时后，Reason 读取共享证据图，提出 typed intent，
scheduler 派发 worker 执行真实命令，结果回写图并触发 review/revalidation，直到满足完成条件或停止。
没有单独的 Race/Coordinator 模式，也没有按阶段切换执行器的兼容分支。

```
① Prepare
   建立本题的 SharedGraph · 暂存附件 · 探活 worker profile ·
   （容器模式）启动运行时并接通 blackboard skill
        │
        ▼
② Reason
   Reason planner 读取图上的事实、死路、未完成 intent 与操作员指令，
   提出带类型和方向的下一步 intent
        │
        ▼
③ Schedule / Execute  ◄──────────────────────────────┐
   ReasonScheduler 从图中选择可执行 intent，worker claim 后运行真实命令 │
        │                                               │
        ▼                                               │
④ Record / Review                                      │
   worker 经 dswarm-blackboard 写回 fact / dead-end / PoC；              │
   flag 仍必须经过 provenance gate；review/revalidation 审计并更新图 ────┘
        │
        ▼
⑤ Finalize
   达成目标、操作员停止或预算耗尽：释放认领、写入唯一 RUN_FINISHED、清扫运行时
```

**核心循环**：Reason 读图 → 提出 intent → worker 认领并执行 → 结果写回图 → review/revalidation
审计 → 下一轮规划。SharedGraph 是持久化事实来源，InsightBus 只负责把新变化及时广播给当前 worker。

> 注意：**ReasonScheduler 在宿主进程内调度并维护运行状态**；worker 是独立 CLI 进程（容器模式还在
> 另一个容器里），它与证据图的交互只能走 `dswarm-blackboard` skill。任何 flag 都必须能追溯到
> worker 的真实 stdout/stderr/artifact 输出，模型声明或操作员提示都不能绕过闸门。

| 阶段 | 什么时候进 | 干什么 | 产出 |
|---|---|---|---|
| **① 准备** | run 一开始 | 建图、暂存附件、探活 profile、准备 worker 运行时 | 可用的运行时与空/初始证据图 |
| **② Reason 规划** | 图有新证据或需要新方向时 | 读取图并提出 typed intent | 可认领的探索、验证或审计任务 |
| **③ 执行与回写** | intent 被 worker 认领后 | 运行真实命令，经 skill 写回结果 | facts / dead-ends / PoCs / 候选 flag |
| **④ Review / revalidation** | 结果需要核验或触发审计时 | 质疑证据、压制重复路线、重新验证候选 | 更可靠的证据图 |
| **⑤ 收尾** | 攒够合规 flag、操作员停止或预算耗尽 | 释放认领、发终态事件、清扫 | 唯一 RUN_FINISHED + 可复盘的图 |

**几个关键点：**
- **同一条主路径**：首批 worker 和后续 worker 都由图上的 typed intent 驱动，不存在旧的 Race 快路径。
- **Reason 是独立阶段**：只有证据图发生有效变化或出现调度需求时才重新规划，避免空转烧钱。
- **Review 是旁路但不越权**：它可以否证事实、重开路线、发起 revalidation，但不能直接制造 flag。
- **收尾幂等且必达**：正常解出、操作员叫停或运行时异常，都会发出唯一终态事件。

## 核心数据通道：dswarm-blackboard skill

worker 是独立的 CLI Agent 进程（容器模式下还在另一个容器里），**够不到协调器的内存**。它能把数据交到平台、也能看到队友的进展，**全靠 `dswarm-blackboard` 这个 skill**——也就是每个 worker 引擎里都装好的命令行脚本 `blackboard.py`。这是 worker 与黑板之间**唯一**的数据通道，也是「群体协作」真正落地的地方。

- **接入方式**：协调器给每个 worker 注入三个环境变量——`DSWARM_BLACKBOARD_DB`（指向这道题的共享 SQLite）、`DSWARM_WORKER_ID`（它是谁）、`DSWARM_INTENT_ID`（它在做哪个 intent）。skill 本体在容器镜像里已内置（源码模式下直接用仓库里的那份），CLI Agent 会自动发现并按需调用。
- **它让 agent 在对的时机做对的事**（纪律写死在 `SKILL.md` 里）：
  - **动手前先读板**：`read-deadends` / `read-review`（别走已被否证或被 Review 压制的路）、`read-facts` / `read-routes` / `read-branches`（捡队友验证过的踏脚石）、`read-flags`（多 flag 题去补缺的那个）、`read-directives`（看操作员指令）。
  - **领活**：`list-intents` → `claim I3`（打印 `WON`/`LOST`，输了就换一个，天然防撞车）。
  - **危险/独占动作前锁资源**：`claim-resource "destructive:tcp:445@host"` / `release-resource`（两个 worker 不会同时打同一个靶 / 端口 / 账号）。
  - **确认了就写回**：`write-fact "..." --verified`（只有真在输出里看到的才加 `--verified`）、`mark-deadend "..."`（写死路和写事实一样有价值）。
- **为什么是 skill 而不是直接写库**：
  1. worker 跨进程 / 跨容器，CLI 脚本是它唯一能用的接口；
  2. `write-fact --verified` 仍要在宿主侧过**闸门 / 见证**校验——agent 自己说「verified」不等于真 verified；
  3. `SKILL.md` 把「何时读、何时写」的纪律直接教给 agent，让它**主动**协作，而不是被动被系统抓取。
- **兜底（不是主路）**：万一 worker 没调 skill，它在输出里打印的 `VERIFIED_FACT=` / `FOUND_FLAG=` 等标记也会被宿主收割进黑板——但那只是安全网，**主通道始终是 skill**。

## 把图里每块拆开讲

- **ReasonScheduler**——宿主上的调度核心，读取 SharedGraph、选择可执行 intent、安排 worker、处理停止/预算/资源约束；它自己不解题。
- **Reason 规划器**——把证据图交给推理模型，判断目标是否达成，未达成就提出下一步 typed intent；规划由有效图变化和调度需求触发。
- **共享黑板 SharedGraph**——每题一个文件、事件溯源的证据图，是**唯一事实来源**。它存 Facts / Intents / Dead-ends / Flags / PoCs。
- **dswarm-blackboard skill**——每个 worker 内置的 `blackboard.py`，是 worker 读写黑板的唯一通道：动手前读已知、领 intent、锁资源、完成后写 fact / dead-end。
- **Worker**——一个带壳的 CLI Agent：认领一个 intent，运行真实命令，到自然退出点结束。所有与黑板的交互都经 skill。
- **闸门 Gate**——整个项目的护城河。一个 flag 必须格式正确、不是占位符，并且逐字出现在真实命令输出里；否则只能作为候选。
- **InsightBus**——SharedGraph 负责持久化和审计，InsightBus 负责把新变化及时广播给正在运行的 worker。

## Worker 的四种角色

所有 worker 都是**单发**的：领一个任务跑完就退，不中途 resume。操作员的指令、队友的发现，都只注入到**下一个**新 worker，而不去搅动正在跑的那个。

| 角色 | 干什么 |
|---|---|
| **bootstrap** | 对图上当前目标做深度冲刺，尝试完成一个初始或重新规划的方向 |
| **explore** | 只认领**一个** typed intent，做窄而专的定向探测 |
| **review** | 审计员：挑战可疑事实、压制重复路线、拆分支；**自己不制造 flag** |

> 没有「卡顿就杀 worker」的机制。worker 的回收只有两种：自然退出，或它认领的 intent **租约过期**被重新派发。

## 核心原语（各种术语的含义）

| 原语 | 含义 |
|---|---|
| **Fact（事实）** | 一条客观、已确认的发现。过了闸门叫 **verified**，没过只算 **candidate（候选，别当真）** |
| **Intent（意图）** | 一个声明出来、还没执行的探索方向。生命周期：**提出 → 认领 → 结论** |
| **Dead-end（死路）** | 一条已被否证的路线，记下来**让所有人别再走**——这是「群体不重复劳动」的关键 |
| **Flag** | 题目答案，只能由闸门接受；支持一题多 flag |
| **PoC** | 可被别的 worker 继承的利用产物（脚本 / payload） |
| **去重三件套** | **route**（同一攻击方向折叠）/ **lane**（危险独占资源串行化）/ **branch**（竞争假设分头证伪），防止 N 个 worker 撞车 |
| **Directive（操作员指令）** | 人的判断作为一等对象注入，agent 下次读板时吸收 |

## 调度：派什么 / 派几个 / 何时停

- **派什么**：Reason 从黑板的证据里提 intent；worker 用 skill `claim` 去认领。
- **派几个**：开局 2 个 bootstrap，普通 worker 上限 ~10；空槽每拍只补 1 个（避免一窝 worker 同生共死、把靶机限流打挂）；优先选**当前没在跑**的引擎（异构互补）。
- **何时停**：**第一个合规 flag 即胜**，其余 worker 立刻取消（多 flag 题则继续凑够数）。CTF 保证有解，所以 swarm **默认永不自己放弃**；只有「连续好几个 worker 毫无产出」时会**软暂停**等人，或操作员手动停。
- **健康降级**：派发前快速探活每个引擎，挂了的临时踢出名册，恢复了再归队。

## 事件架构

核心和前端之间**只有一个契约：一条有类型、有序、带单调序号的事件流**。

- **EventBus**：核心把每件事（worker 上下线、工具调用、证据进图、flag 找到、worker 举手…）发到一根进程内的 pub/sub 脊椎；带环形回放 + 落盘（每 run 一个 JSONL）。
- **前端是哑订阅者**：Web 指挥台和 TUI **从不直接调核心**，只做两件事——**订阅事件流**（SSE，断线用 Last-Event-ID 续传）和 **POST 命令**。所以两个前端完全可互换。
- **HITL 回路（人 → 核心）**：操作员的 `提示 / 改向 / 暂停 / 继续 / 停止 / 判假 flag / spawn / kill` 都是 POST 进一个队列，协调器在循环里消费。注意是**单发架构**——指令不会打断正在跑的 worker，而是注入**下一个**新 worker。
- **worker 举手（核心 → 人）**：worker 缺只有人能给的东西（VPS、凭证）或环境挂了，会发 `HITL_REQUEST`，协调器暂停这条方向等人，而不是傻乎乎拿更多 worker 去撞墙。

---

## 最外层（一句话带过）

最外面还有一层**运行后端**：`local` 直接在宿主跑 CLI（最快）；`container` 把 worker 关进 Kali 工具容器，worker **不开任何端口**，由容器内一个 Go supervisor **反向拨号**回宿主、宿主再把启动/信号命令发回去（一个 run 一条连接、按 worker 标识复用）。这层只搬运进程、保证工具链一致和按 run 隔离，**不参与任何解题判定**。

## 术语速查

| 术语 | 含义 |
|---|---|
| **dswarm-blackboard skill** | 每个 worker 内置的 `blackboard.py`，是 worker 读/写黑板的**唯一通道**（读已知、领 intent、锁资源、写 fact/dead-end） |
| **single-shot（单发）** | worker 领一个任务跑完就退，不中途 resume；指令只影响下一个 worker |
| **bootstrap / explore / respond / review** | 整题启动 / 单 intent 定向 / 操作员响应 / 审计与重验证，四种 worker 角色 |
| **ReasonScheduler** | 读取 SharedGraph、派发 typed intent、触发 review/revalidation；不直接执行题目命令 |
| **Reason 规划器** | deepseek，读黑板吐 intent；图变化时才触发 |
| **SharedGraph / 黑板** | 每题一个、事件溯源的证据图，唯一事实来源 |
| **InsightBus** | 黑板旁的内存广播，把新事实即时推给在跑的队友 |
| **Gate（闸门）** | 唯一硬编码、不可插拔的 flag 接受函数：格式 + 非占位符 + 逐字溯源 |
| **Fact / candidate / verified** | 客观发现 / 没过闸门的候选 / 过了闸门的已验证 |
| **Intent** | 待执行方向，提出→认领→结论 |
| **Dead-end** | 已否证的死路，防重试 |
| **route / lane / branch** | 方向去重 / 危险资源独占 / 竞争假设分支 |
| **Directive** | 一等的人工指令 |
| **first-valid-flag-wins** | 第一个过闸门的 flag 即胜，其余 worker 取消 |
| **HITL** | 人在环：人发命令 / worker 举手要资源 |
| **local / container 后端** | 宿主直跑 / Kali 容器反向连接隔离 |
